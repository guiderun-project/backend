                 GuideRun 백엔드 에러 확인 방법 안내서
================================================================================
작성일: 2026-06-18
대상: Spring Boot 3.1.7, Java 17, Gradle
기본 작업 폴더: backend/run

--------------------------------------------------------------------------------
1. 로그 파일 위치
--------------------------------------------------------------------------------

애플리케이션을 실행하면 프로젝트 루트(run 폴더) 안에 logs 폴더가 자동으로 생깁니다.

  backend/run/logs/
  ├── guiderun-app.log       (모든 INFO 이상 로그가 여기에 저장됩니다)
  ├── guiderun-error.log     (ERROR 레벨 로그만 따로 저장됩니다)
  └── guiderun-http.log      (HTTP 요청/응답 로그가 저장됩니다)

중요: error.log 파일만 확인하면 서버 에러(500번대)를 빠르게 파악할 수 있습니다.

--------------------------------------------------------------------------------
2. 로그 파일별 역할
--------------------------------------------------------------------------------

[guiderun-app.log]
  - 서버가 시작할 때부터 종료할 때까지 모든 정보가 기록됩니다.
  - INFO, WARN, ERROR 레벨 모두 포함합니다.
  - 파일 크기가 10MB를 넘으면 날짜별로 자동 분리됩니다.
  - 30일이 지난 파일은 자동으로 삭제됩니다.

[guiderun-error.log]
  - ERROR 레벨 메시지만 기록합니다.
  - 서버가 예상치 못한 오류를 냈을 때 여기서 확인하면 됩니다.
  - 에러 발생 시 아래 정보가 함께 기록됩니다:
      URI  : 어떤 주소(URL)로 요청했을 때 에러가 났는지
      IP   : 요청한 사람의 IP 주소
      USER : 로그인한 사용자 ID (로그인 상태인 경우)
      MSG  : 에러 메시지
      스택트레이스 : 에러가 발생한 코드의 정확한 위치
  - 60일이 지난 파일은 자동으로 삭제됩니다.

[guiderun-http.log]
  - 모든 HTTP 요청(Request)과 응답(Response)이 기록됩니다.
  - 어떤 API가 얼마나 걸렸는지, 상태 코드가 무엇인지 확인할 수 있습니다.
  - 7일이 지난 파일은 자동으로 삭제됩니다.

--------------------------------------------------------------------------------
3. 로그에서 에러 찾는 방법
--------------------------------------------------------------------------------

[방법 1] error.log 파일을 텍스트 편집기로 열어서 확인

  1. backend/run/logs/guiderun-error.log 파일을 엽니다.
  2. 가장 최근 줄이 가장 최근 에러입니다.
  3. 에러 한 건은 아래와 같은 형태로 기록됩니다:

      2026-06-18 15:30:12.456 [http-nio-8080-exec-1] ERROR com.guide.run.event.service.EventService
        URI : /api/event/1234
        IP  : 192.168.0.10
        USER: user_socialId_001
        MSG : 이벤트를 찾을 수 없습니다
        (스택트레이스가 이어서 출력됩니다)

[방법 2] 콘솔(터미널) 출력에서 직접 확인 (로컬 개발 환경)

  bootRun 실행 중 터미널에서 아래 키워드를 찾으면 됩니다:

  - [ERROR]      : 서버 내부 오류 (즉시 확인 필요)
  - [WARN]       : 클라이언트 오류 또는 예상 가능한 예외
  - [REQ]        : 요청 시작 (어떤 URL로 요청이 들어왔는지)
  - [RES]        : 응답 완료 (상태 코드와 처리 시간)
  - [EXCEPTION]  : 예외 처리 핸들러가 동작했을 때
  - [서버 오류]  : 처리되지 않은 예외 발생

  예시 정상 흐름:
    15:30:12.100 INFO  [REQ] [a1b2c3d4] POST /api/event | IP=127.0.0.1
    15:30:12.350 INFO  [RES] [a1b2c3d4] POST /api/event | STATUS=201 | 250ms

  예시 에러 흐름:
    15:31:00.100 INFO  [REQ] [e5f6a7b8] GET /api/event/9999 | IP=127.0.0.1
    15:31:00.105 WARN  [EXCEPTION] handler=NotExistEventException | type=NotExistEventException | msg=...
    15:31:00.106 WARN  [RES] [e5f6a7b8] GET /api/event/9999 | STATUS=404 | 6ms

4. HTTP 상태 코드별 의미
--------------------------------------------------------------------------------

200번대 (성공)
  200 OK          : 정상 처리됨
  201 Created     : 새 데이터 생성 성공

400번대 (클라이언트 오류 - 요청 내용 문제)
  400 Bad Request : 잘못된 요청 형식 또는 값
  401 Unauthorized: 로그인 필요 또는 토큰이 만료됨
  403 Forbidden   : 권한 없음 (로그인은 됐지만 접근 불가)
  404 Not Found   : 요청한 데이터가 존재하지 않음

500번대 (서버 오류 - 코드 문제)
  500 Internal Server Error: 서버 내부 오류 (즉시 에러 로그 확인 필요)

--------------------------------------------------------------------------------
5. 에러 코드 체계 (응답 JSON의 code 필드)
--------------------------------------------------------------------------------

응답 예시:
  {
    "isSuccess": false,
    "code": "1300",
    "message": "존재하지 않는 사용자입니다"
  }

에러 코드 분류:
  0000       : 알 수 없는 서버 내부 오류
  0100-0199  : 인증 토큰 관련 오류 (JWT)
  1000-1099  : 사용자 권한 오류
  1100-1199  : 사용자 입력값 오류 (DTO)
  1200-1299  : 사용자 비즈니스 로직 오류
  1300-1399  : 사용자 리소스 없음 오류
  2000-2099  : 이벤트 권한 오류
  2100-2199  : 이벤트 DTO 오류
  2200-2299  : 이벤트 비즈니스 로직 오류
  2300-2399  : 이벤트 리소스 없음 오류
  3000번대   : 관리자 관련 오류

6. bootRun 실행 후 자주 발생하는 에러 유형과 해결 방법
--------------------------------------------------------------------------------

[에러 유형 1] 환경 변수 없음 오류
  증상: 서버 시작 실패, 아래와 같은 메시지
        Could not resolve placeholder '${TEST_RDS}'

  원인: 데이터베이스 주소, 비밀번호 등 환경 변수가 설정되지 않았습니다.

  해결:
    1. IntelliJ IDEA 사용 시:
       Run > Edit Configurations > Environment variables에
       아래 항목들을 추가합니다:
         TEST_RDS=jdbc:mysql://DB주소:3306/DB이름
         MYSQL_USERNAME=사용자이름
         MYSQL_PASSWORD=비밀번호
         S3_BUCKET=버킷이름
         S3_ACCESS=액세스키
         S3_SECRET=시크릿키
         SMS_KEY=쿨SMS API키
         SMS_SECRET=쿨SMS API시크릿
         SEND_NUMBER=발신번호
         ADMIN_NUMBER=관리자번호
         KAKAO_CH_ID=카카오채널ID
         SIGNUP_COMPLETE_MSG=가입완료메시지ID
         SIGNUP_APPROVAL_MSG=승인메시지ID
         KAKAO_CLIENT_ID=카카오클라이언트ID
         CLOUD_FRONT_URL=클라우드프론트주소

    2. 터미널(Gradle)에서 실행 시:
       export TEST_RDS=... 처럼 환경 변수를 먼저 설정한 후 bootRun을 실행합니다.

[에러 유형 2] 데이터베이스 연결 실패
  증상: 서버 시작 실패
        Communications link failure
        Unable to acquire JDBC Connection

  원인: 데이터베이스 서버에 연결할 수 없습니다.

  해결:
    1. 데이터베이스 서버가 실행 중인지 확인합니다.
    2. 환경 변수에 입력한 DB 주소, 포트, 사용자 이름, 비밀번호가 맞는지 확인합니다.
    3. 방화벽 또는 네트워크 설정이 연결을 차단하고 있는지 확인합니다.

[에러 유형 3] Redis 연결 실패
  증상: 서버 시작 실패 또는 로그인 시 에러
        Unable to connect to Redis

  원인: Redis 서버가 실행되지 않았거나 연결 설정이 잘못됐습니다.

  해결:
    1. 로컬에 Redis가 설치됐다면 redis-server 명령어로 실행합니다.
    2. application-local.yml에 Redis 설정을 확인합니다.

[에러 유형 4] JWT 토큰 오류
  증상: API 호출 시 401 응답
        code: "0100" - 유효하지 않은 accessToken
        code: "0101" - 인증 사용자 없음

  원인: 로그인 토큰이 만료됐거나 잘못됐습니다.

  해결:
    1. 다시 로그인해서 새 토큰을 발급받습니다.
    2. 개발 중이라면 Swagger UI (/swagger-ui.html) 에서 Authorize 버튼으로
       새 토큰을 등록합니다.

[에러 유형 5] 처리되지 않은 서버 오류 (500)
  증상: API 호출 시 500 응답, code: "0000"

  원인: 예상하지 못한 예외가 발생했습니다.

  해결:
    1. guiderun-error.log를 엽니다.
    2. [처리되지 않은 예외] 키워드를 찾습니다.
    3. 스택트레이스에서 com.guide.run 으로 시작하는 줄을 찾으면
       에러가 발생한 정확한 클래스와 줄 번호를 확인할 수 있습니다.

7. 로그 레벨 설명
--------------------------------------------------------------------------------

  TRACE : 가장 상세한 정보. SQL 파라미터 값 등 매우 자세한 내용.
          (로컬 환경에서만 활성화)

  DEBUG : 개발 디버깅용 상세 정보.
          (로컬, 개발 환경에서 활성화)

  INFO  : 일반 처리 흐름. 정상 동작 중 주요 이벤트.
          (모든 환경에서 활성화)

  WARN  : 클라이언트 오류(4xx), 예상 가능한 예외 상황.
          (모든 환경에서 활성화)

  ERROR : 서버 내부 오류(5xx). 즉시 확인 필요.
          (모든 환경에서 활성화, error.log에 별도 저장)

--------------------------------------------------------------------------------
8. 환경별 로그 설정 차이
--------------------------------------------------------------------------------

  로컬(local)   : DEBUG 레벨. 콘솔 + 파일에 모두 출력. SQL 쿼리도 출력.
  개발서버(dev) : INFO 레벨. 콘솔 + 파일에 모두 출력.
  운영서버(prod): INFO 레벨. 파일에만 출력 (콘솔 없음).

  로컬에서 SQL 쿼리가 너무 많이 출력되면 application-local.yml 에서
  아래 줄의 레벨을 DEBUG에서 INFO로 바꾸면 숨길 수 있습니다:
    org.hibernate.SQL: DEBUG  ->  org.hibernate.SQL: INFO

--------------------------------------------------------------------------------
9. 로그 파일 내용 검색 팁 (Windows 기준)
--------------------------------------------------------------------------------

  메모장, 메모장++, VS Code 등의 텍스트 편집기에서 파일을 열고
  Ctrl+F (찾기)로 아래 키워드를 검색하면 빠르게 찾을 수 있습니다:

    ERROR              : 모든 에러 찾기
    [처리되지 않은 예외]  : 예상 못한 서버 오류 찾기
    STATUS=5           : 500번대 응답 찾기
    STATUS=4           : 400번대 응답 찾기

  특정 API 에러를 찾을 때:
    /api/event      : 이벤트 관련 에러만 찾기
    /api/user       : 사용자 관련 에러만 찾기
